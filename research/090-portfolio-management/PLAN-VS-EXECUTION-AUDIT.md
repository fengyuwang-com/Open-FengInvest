## 三、关键偏差分析

### 偏差 #1（最大）：数据质量验证完全缺失

**计划的盲区：** 改进计划聚焦于 AI **执行步骤**的强制性和可验证性，但从未考虑**数据准确性**的验证。

**实际后果：** 腾讯分析的 PE 数据错误（22x 搜索估算 vs 16.2x 真实值）通过了所有 8 层验证：
- fengstate.py verify → ✅ 文件存在、格式正确
- fengstate.py accept → ✅ key_fields 齐全
- 独立验证门禁 → ✅ 文件结构完整
- 跨层一致性检查 → ⚠️ 只检查 L1 vs L2b 信号冲突，不检查 PE 绝对值

**发现问题的是用户，不是系统。**

### 偏差 #2：结构化输出模板只落地 60%

计划要求**全部 8 层**都采用 `.json + .md` 双格式。实际只给 01-capability、06-collision、08-portfolio 部分实现了 JSON 结构，05-qualitative 仍为纯 markdown。

这个偏差有现实理由：05-qualitative 包含四大师的长篇分析，强转 JSON 会丢失可读性。但缺少结构化摘要意味着碰撞引擎（fengcollision.py）无法直接读取 L2a 结果，只能靠 `proxy_l2a_lights()` 的字符串匹配，增加了出错风险。

### 偏差 #3：yfinance 限流造成系统性降级 — 计划的弹性策略不够

**计划中的弹性策略**：retry 3次 → 降级标记

**实际表现**：3次重试全部失败 → 数据降级 → 手动填补 → 填补数据有误 → 用户纠正

问题不在重试次数，而在于：
1. yfinance 的通用限流（JP/US/SG 全部限流）不是临时故障而是结构性问题
2. "降级 = 搜索替代"这条路径不可靠 — 搜索数据精度不够（PE 22x vs 16.2x 差 36%）

### 偏差 #4：Phase 5 被 Stop Hook 强制完成，超出原始计划范围

计划将 Phase 5 标注为 "Low Priority / Stretch Goals"。Stop Hook 检测到 Phase 5 标记为"待定"后阻止了会话结束，强制全部实现。

结果：4 项都完成了，但这是在计划说明 "Low Priority" 的前提下被外部机制推动的。

### 偏差 #5：verify-layer 子 skill（Phase 4）被简化

计划说要创造独立 `Skill("fenginvest-verify")` 子 skill。实际只内嵌为 Step 6.5。这削弱了验证的独立性——验证逻辑仍然在主 skill 中，无法被独立调用。

### 偏差 #6：缺少非功能性需求验证

系统验证了：
- 文件是否存在 ✅
- 关键字段是否齐全 ✅
- 层间依赖是否满足 ✅

但没有验证：
- 数据是否准确（PE 对了吗？）❌
- 逻辑是否一致（安全边际判断与 PE 值匹配？）❌
- 来源是否可靠（用的搜索估算还是真实数据源？）❌

## 四、做对了的地方

1. **状态机物理强制的设计决策被验证是正确的。** 8 层全部按序完成，没有跳步。即使所有工具都限流降级，流程也没乱。

2. **Phase 3 弹性模式（retry → degrade）在极端条件下仍然有效。** yfinance 全节点限流时，降级标记让分析可以继续，而不是卡死在 Step 0。

3. **Phase 5 的 4 项改进全部正确落地。** 特别是 execution_log 和智能跳步，解决了之前无法审计 AI 行为和"不懂"后强行分析的问题。

4. **反方强制检查（4问）有效阻止了确认偏误。** 碰撞引擎要求回答"5种亏钱方式"、"跌30%加仓还是割肉"等，暴露了风险。

5. **PE 修正的级联更新机制是正确的。** 用户指出错误后，修正从 M 层→L2b→L3→L4→P 级联更新，每条路径都是正确的（6个文件一致更新，没有遗漏）。

6. **主 skill 整合策略已验证。** 用户要求"只需要一个 fenginvest"，将 8 个分离的子 skill 合并为单一指令，减少了碎片化和维护成本。

## 五、做错了 / 不够的地方

1. **❌ 数据没有第二信源验证。** PE 22x（错误）从搜索估算写入 M 层后，后续 5 层全部基于这个错误值分析。没有一个机制说"等一下，这个 PE 值和直觉/历史/同行差太多，验证一下"。

2. **❌ yfinance 限流后的降级路径不可靠。** 搜索替代数据的质量未经检验。应补充 stockanalysis.com / aastocks / macrotrends 等可靠信源作为第二数据管道。

3. **❌ 状态机验证全是结构性的，没有语义验证。** "文件存在"、"字段齐全"验证了形式，但不验证内容。PE 16.2x 和 22x 都通过同样的验证。

4. **❌ Phase 4 的独立验证被简化，丧失了独立性。** 内嵌在 SKILL.md 的 Step 6.5 本质上是自我验证，不是独立的第三方检查。

5. **❌ 结构化输出模板只完成 60%。** 05-qualitative 缺失结构化摘要，导致碰撞引擎无法直接读取 L2a 结论，只能用字符串匹配回退。

6. **❌ /fenginvest 全流程执行了 18+ 个搜索和工具调用，大量超时/限流/404。** 会话可见大量 Exit code 143 (timeout)、Exit code 1 (error)、File does not exist 错误。效率低，用户体验差。

7. **❌ 跨层一致性检查（Phase 5）覆盖面太窄。** 只检查了 L1 vs L2b 信号冲突 / M层趋势 vs L1均线 / M层估值 vs L1真价值 三组。没有检查"M层的 PE 值是否与 L2b 的因子分析使用的 PE 值一致"。

## 六、根本原因总结

```
┌─────────────────────────────────────────────────────┐
│                    根本原因                          │
├─────────────────────────────────────────────────────┤
│                                                     │
│  1. 验证哲学偏差：重"步骤"轻"数据"                  │
│     → 状态机保证步骤按序执行，不保证数据准确        │
│     → 所有验证都是结构性的（文件/字段），非语义的    │
│                                                     │
│  2. 数据管道脆弱：单一信源（yfinance）               │
│     → yfinance 限流 → 搜索替代 → 精度不足          │
│     → 无第二数据管道交叉验证                        │
│                                                     │
│  3. 降级策略缺监控：降级后无"额外验证"要求           │
│     → 标记 degraded 就继续，但不要求降级数据交叉验  │
│                                                     │
│  4. 计划设计时未覆盖端到端数据质量                    │
│     → 改进计划关注 AI 行为（会不会跳步）           │
│     → 不考虑 AI 产出（做出的判断对不对）           │
│                                                     │
└─────────────────────────────────────────────────────┘
```
